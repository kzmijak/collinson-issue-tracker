# Enrichment report — 002-early-alpha-issues-reader

2026-09-12T09:23:12.517Z · written · 1m 58s · 148,023 ET

## Assumptions made

- **Exact tracker comment author string to check for prior touch** "GitHub Issues Tracker" — matches the example print in 2026-09-12 Mock GitHub Improvements
- **Default port/poll-interval numbers, not stated in prose** 4000 and 2000ms — arbitrary but stable defaults, both overridable via env

## Expected drawbacks

- Comment-added log line and the next full repaint can interleave in real terminals, meaning transient duplicate-looking lines outside snapshot boundaries — acceptable since accs only inspects the region between markers.
- Author-name matching for 'already touched' is spoofable (anyone can post as 'GitHub Issues Tracker') but that's fine for a mock-only, single-tracker scenario.

## Contract

| facade | promise |
| ------ | ------- |
| pnpm mock-github | Starts the In-Memory Stateful Fake GitHub Service: an HTTP server plus a terminal renderer sharing the same in-memory state. Loads 60% of mock issues immediately, the rest linearly over the next 10 seconds, per spec 001. |
| env MOCK_GITHUB_PORT (default 4000) | Port the Mock GitHub HTTP server listens on. |
| GET /issues | Returns JSON array of current issues, each with id, title, content, and a comments array (author, body, createdAt). Reflects the exact in-memory state at call time. |
| POST /issues/:id/comments  { "author": string, "body": string } | Appends a comment to issue :id in memory, returns the updated issue JSON (including new comment count) with status 201. Returns 404 if the issue id doesn't exist. |
| stdout marker line: "===SNAPSHOT <n> <isoTimestamp>===" | Printed as the very first line every time the Mock GitHub terminal repaints. n is a monotonically increasing integer starting at 0. Everything printed between two consecutive markers (or after the last one) is one complete, self-contained screen — no issue repeats within it. |
| Mock GitHub terminal issue line format: "Issues #<id>: (<commentCount>)" | Comment count shown next to each issue always matches comments.length from GET /issues at render time. |
| Mock GitHub terminal comment-added log line: "[comment] issue #<id> +1 from <author>" | Printed once, immediately, every time POST /issues/:id/comments succeeds — independent of and prior to the next scheduled repaint. |
| Mock GitHub terminal truncation line: "..." | If the full issue listing can't fit inside the buffer line-limit, the screen is cut short and its last line is exactly "..." — that line itself counts toward the limit. |
| Mock GitHub terminal buffer size = min(process.stdout.rows, 200), or 200 when stdout is not a TTY | This is the hard cap on lines printed per screen, snapshot marker line included. |
| pnpm issues-tracker | Starts the Proactive Issues Tracker. Polls GET /issues on the Mock GitHub service, and for every issue with no comment whose author is exactly "GitHub Issues Tracker", POSTs a comment { author: "GitHub Issues Tracker", body: "I've been here!" } exactly once. |
| env MOCK_GITHUB_URL (default http://localhost:4000) | Base URL the Issues Tracker polls against. |
| env ISSUES_TRACKER_POLL_INTERVAL_MS (default 2000) | Interval between Issues Tracker poll cycles. |

## ACCS — general flow

1. Guard: refuse to run if MOCK_GITHUB_URL points at real GitHub or a GITHUB_TOKEN is set
2. Run spec 001's accs.bash; if it fails, dump its log and terminate this script with an error; if it passes, kill any leftover process tree it spawned and continue
3. Start `pnpm mock-github`, wait for its HTTP server to respond, record the spawn timestamp
4. GET /issues right after boot: confirm at least one issue is loaded and none of them have any comments yet
5. Sleep until 4s have elapsed since spawn, GET /issues again: confirm the issue count grew from the first read
6. Run parse-snapshots.mjs over the mock-github log: every '===SNAPSHOT n===' block must have strictly increasing n, no issue id repeated within one screen, line count within the buffer cap, and a literal '...' as the last line whenever the cap was hit
7. POST a 'Hello World!' comment (author Tester) to the first issue via curl
8. Assert the '[comment] issue #<id> +1 from Tester' log line appeared immediately, and GET /issues shows that issue now has exactly 1 comment
9. Run `pnpm issues-tracker` for a couple of poll cycles against the mock service, then kill it
10. GET /issues one last time: first issue must have exactly 2 comments including one from 'GitHub Issues Tracker' saying "I've been here!"; every other issue has 0 or 1 comment, and if 1 it must be that exact tracker comment
11. Re-run parse-snapshots.mjs over the full mock-github log to confirm no issue was ever duplicated on a single screen across the whole run
12. Clean up both spawned processes on exit and report pass/fail
