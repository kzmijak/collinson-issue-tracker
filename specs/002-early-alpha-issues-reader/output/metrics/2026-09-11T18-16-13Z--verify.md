# Verification report — 002-early-alpha-issues-reader

2026-09-11T18:15:22.992Z · rejected · 51s · 67,496 ET

## Summary

The ACCS never actually confirms a repaint prints every issue together in one shot — it only checks that each issue line shows up somewhere in the log at some point, so a diff-style repainter (explicitly forbidden by the contract) would still pass.

## Scope of the fix

Redo the ACCS only.

## Why rejected

- **Coverage** "[ "$TOTAL_COUNT_LINES" -gt "$ISSUE_COUNT" ] \
  || fail "terminal only printed one repaint's worth of lines ($TOTAL_COUNT_LINES), expected multiple repaint cycles over ~4s"" — This only checks a raw total line count across the whole run, not that any single repaint block contains all currently-loaded issue numbers. A tracker that logs only the issue whose count just changed (a diff, not a full repaint) can still accumulate more lines than ISSUE_COUNT over ~4s of backfill + comment events, and would still make every per-issue grep in the loop above pass since each issue gets logged at least once when it's added or touched.
- **Coverage** "grep -Eq "Issue #${num}: [0-9]+ comment\(s\)" "$MOCK_LOG" \
    || fail "GitHub Service Terminal never printed a comment-count line for issue #$num"" — This is satisfied by a single appearance of the line anywhere in the whole log, which is exactly the shape a diff-based repaint would also produce. Nothing in this script groups lines by repaint cycle (e.g. by timestamp, blank-line separators, or a repaint marker) to verify all issues appear together, so the explicit contract line 'never a diff or an append' and the 'terminal repaint' behaviour row are effectively untested.
