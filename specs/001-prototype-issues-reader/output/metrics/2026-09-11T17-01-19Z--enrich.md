# Enrichment report — 001-prototype-issues-reader

2026-09-11T16:59:20.151Z · written · 1m 59s · 209,490 ET

## Assumptions made

- **what HTTP path the mock exposes for issues** GET /repos/{owner}/{repo}/issues, matching real GitHub's REST shape, where {owner}/{repo} together equal the single GITHUB_REPO value
- **what port the mock listens on by default** 4123, overridable via MOCK_GITHUB_PORT
- **how to identify a genuine issue line in tracker output without naming src internals** require the issue's own number (fetched independently via curl) to appear as a whole word on a line that is not the Polling status line
- **how to verify 'Only display active issues' without runtime mutation of the mock dataset** require the mock's fixed seed data to contain at least one closed issue and assert its number is absent from tracker output throughout the run
- **how to stop accs.bash from hanging forever on a dead dependency** 5s --max-time per curl plus a 60s `timeout` wrapper around the whole script body
- **how to keep the growth-window assertion valid regardless of boot-loop duration** anchor the 10s growth wait to the timestamp of the first successful boot curl, not to process spawn time
- **how to guarantee clean process teardown across runs** launch via setsid, kill the whole process group on exit, and use per-run-unique log filenames instead of truncating shared ones

## Expected drawbacks

- Measuring the 10s growth window from first successful curl instead of process spawn means a very slow machine could still see the mock finish growing before TOTAL1's own retry loop gives up — accepted risk, not solved here.
- Process-group kill via setsid requires the runtime to support it; on environments without setsid this teardown step degrades to best-effort PID kill only.

## ACCS — general flow

1. Self-wrap under `timeout 60` on first invocation so the whole check dies on schedule.
2. Launch mock-github and prototype-issues-reader as setsid process-group leaders, logging to run-unique files; register a trap to kill both groups on exit no matter what.
3. Poll GET /repos/${GITHUB_REPO}/issues (via curl --max-time 5, parsed with a node one-liner) until it answers; record that moment as TOTAL1 and capture the 15-issue open/closed split.
4. Poll the tracker log for up to 20s: fail fast if the closed issue's number ever shows up outside the Polling line, succeed once every open issue's number has appeared as a whole word on a non-Polling line.
5. Snapshot the tracker log's current line count for the later append-only diff.
6. Sleep out the remainder of the 10s growth window measured from TOTAL1, then curl again (TOTAL2) and assert the count grew and the split changed.
7. Sleep 3s to let the tracker's poll loop catch up, then confirm every newly-opened issue number appears unprompted and the closed issue still never appears.
8. Diff the tracker log's first N lines against the earlier snapshot to prove nothing already printed was rewritten.
9. Sample the tail of the tracker log twice ~1.4s apart (up to 3 tries) looking for two different 'Polling' + 1-3-dot lines to prove the status bar is alive.
10. Print ACCS PASS and exit 0 if every stage held; any failed stage calls fail(phase) which logs the phase and exits 1, and the EXIT trap always kills both process groups either way.
