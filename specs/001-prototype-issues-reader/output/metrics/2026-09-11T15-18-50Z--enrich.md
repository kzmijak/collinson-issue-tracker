# Enrichment report — 001-prototype-issues-reader

2026-09-11T15:17:20.004Z · written · 1m 30s · 203,444 ET

## Assumptions made

- **what HTTP path the mock exposes for issues** GET /repos/{owner}/{repo}/issues, matching real GitHub's REST shape, so swapping GITHUB_API_URL is truly plug&play
- **what port the mock listens on by default** 4123, overridable via MOCK_GITHUB_PORT, since none was specified in the prose
- **how to identify a genuine issue line in tracker output without naming src internals** require the issue's own number (fetched independently via curl) to appear as a whole word on a line that is not the Polling status line
- **how to verify 'Only display active issues' without runtime mutation of the mock dataset** require the mock's fixed seed data to contain at least one closed issue and assert its number is absent from tracker output throughout the run
- **how to stop accs.bash from hanging forever on a dead dependency** 5s --max-time per curl plus a 60s `timeout` wrapper around the whole script body

## Expected drawbacks

- A hard 60s ceiling means a legitimately slow CI box could false-fail; accepted per project principles (speed over diligence at this stage)
- Requiring a closed issue in the static seed dataset is a new constraint on mock-github's mock data that spec.md never stated explicitly — it's inferred purely to make 'active only' testable

## Contract

| facade | promise |
| ------ | ------- |
| bash specs/001-prototype-issues-reader/output/accs.bash | single entry point, exits 0 when the world matches this spec, exits 1 otherwise, and never blocks past its own internal deadline |
| GET /repos/{owner}/{repo}/issues | mock GitHub API's issues endpoint, mirrors real GitHub REST shape including a per-issue `state` field of 'open' or 'closed' |
| pnpm mock-github | starts the HTTP server, seeded with 15 issues at boot (including at least one closed issue, fixed at code-time), growing to 20 over the next 10s |
| pnpm prototype-issues-reader | console process printing every open issue's number as a whole word outside the Polling line, appending only, never printing a closed issue's number, with a live Polling status line with 1-3 cycling dots |
| every curl call inside accs.bash | invoked with --max-time 5, so a hung or absent mock-github fails that step within 5s instead of hanging |
| accs.bash process itself | wrapped end-to-end in `timeout 60`, so any stuck step (curl, background process boot, sleep-based waits) forces a non-zero exit at 60s instead of hanging forever |

## ACCS — general flow

1. Re-exec itself once under `timeout 60` so the whole run has a hard deadline
2. Boot pnpm mock-github in the background, logging to mock.accs.log, and retry-curl its /repos/{owner}/{repo}/issues until it answers (each curl capped at --max-time 5)
3. Parse the first response with node (no jq/regex), record total/open/closed counts and issue numbers, and fail if there aren't >=15 issues or no closed issue at all
4. Boot pnpm prototype-issues-reader in the background, wait the 4s post-start window, then assert every open issue number appears as a whole word outside any 'Polling' line and no closed issue number appears anywhere
5. Snapshot the tracker log's current line count for the later append-only diff
6. Wait out the remainder of the mock's 10s growth window plus a 3s growth wait, then curl again and confirm the dataset count grew
7. Wait a 3s settle period, then re-check that all newly-open issue numbers show up unprompted and no closed numbers (old or new) leaked in
8. Byte-diff the tracker log's first L lines against the earlier snapshot to prove nothing was cleared or reordered
9. Sample the tracker log for a 'Polling' line with 1-3 dots twice ~1.4s apart (up to 3 attempts) and require the two samples to differ, proving the status bar is live
10. Kill both background processes via an EXIT trap, clean up scratch files, and exit 0 only if every phase above passed - otherwise exit 1 with the failing phase name printed
