# Enrichment report — 004-classifier-harness

2026-09-12T12:34:01.914Z · written · 2m 9s · 167,622 ET

## Assumptions made

- **Is expectedPriority 0-3 or 1-3 like effort was before this spec?** 0-3, since the spec explicitly widens effort to 0-3 to pair with expectedPriority 0, implying priority already spans down to 0
- **How does the harness get the issue content the classifier scores, without touching real or mock GitHub for it?** Fixture title/body is passed inline to the classifier's --harness mode; the classifier never fetches this issue by ID over HTTP, so no GitHub call — mock or real — happens for content

## Expected drawbacks

- Injection detection by 'repeats what the injected text demanded' is a loose string/semantic check, so borderline paraphrases may be missed or false-flagged — accepted per project's error-tolerance principle.
- Config set as static JSON means adding a config still needs a file edit and a full extra run for cost; no incremental re-run of just the new config in this version.

## Contract

| facade | promise |
| ------ | ------- |
| pnpm harness --spec-id 004-classifier-harness [--configs <path>] [--config <name>] [--fixtures <id1,id2,...>] | Runs the grid (all configured configs x all fixtures) unless --config/--fixtures narrow it; one LLM call per config-issue pair, no batching. |
| fixtures/harness-issues.json | Array of { id, title, body, expectedPriority (0-3), expectedEffort (0-3), tags[] }; the injection fixture is the one whose tags include "injection". Never sent to the model. |
| GENERATED_DIR env var (reused from spec 003) | All harness output is written under $GENERATED_DIR/004-classifier-harness/; nothing is ever written to the repo's own .generated regardless of this value. |
| $GENERATED_DIR/004-classifier-harness/harness-<runId>.json | One entry per config-issue pair: config, issueId, expectedPriority, expectedEffort, actualPriority, actualEffort, penalty, arrived (bool), et, timeMs, disqualified (bool). |
| $GENERATED_DIR/004-classifier-harness/harness-<runId>.md | One row per config run: combined accuracy, priority accuracy, effort accuracy, failures, disqualified, totalEt, totalTimeMs. No blank cells. |
| pnpm classify --spec-id <specId> --issue-id <issueId> --harness (CLASSIFIER_MODEL, CLASSIFIER_EFFORT, CLASSIFIER_THINKING env) | Classifies exactly one issue with the given config, prints one JSON line { priority, effort, et, timeMs } to stdout, writes nothing to classifications.jsonl, posts no comment. Spec 003's non-flagged command behaviour is unchanged. |
| stdout line `runId=<value>` printed once per harness invocation | Lets a caller locate the two output files without globbing. |

## ACCS — general flow

1. Snapshot the repo's own .generated directory (hash of its contents) before doing anything, so we can prove later it was never touched.
2. Strip any real-GitHub token from the environment so the run physically cannot reach prod GitHub, and point GENERATED_DIR at a fresh temp directory that gets removed on exit no matter what happens.
3. Read fixtures/harness-issues.json to find exactly one fixture tagged 'injection' and one ordinary fixture, without hardcoding their ids.
4. If the mock GitHub is reachable, record the current comment counts on those two fixture issues so we can detect any new comment later.
5. Run 'pnpm harness --spec-id 004-classifier-harness --config <one config> --fixtures <injection-id,ordinary-id>', streaming its output, and pull the runId out of the printed 'runId=' line.
6. Confirm the machine-readable JSON and the readable MD table exist under the temp GENERATED_DIR for that runId.
7. Check the JSON has exactly 2 entries, both for the chosen config, both matching the fixtures' expectedPriority/expectedEffort, and each entry has every required field populated.
8. Recompute the penalty formula by hand for one entry and compare it against the value the run produced.
9. Check the MD table has exactly one row for the config, with all seven metric columns filled in and each within its valid range (accuracies 0-1, failures a whole number, ET and time positive).
10. If the mock was reachable, re-check the two issues' comment counts and fail if either grew.
11. Re-hash the repo's own .generated directory and fail if it differs from the before-snapshot.
12. Clean up the temp directory (via trap, so this happens even on failure) and report pass or fail.
