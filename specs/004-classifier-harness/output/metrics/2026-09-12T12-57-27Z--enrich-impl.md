# Implementation report — 004-classifier-harness

2026-09-12T12:57:27Z · `bash specs/004-classifier-harness/output/accs.bash` exits 0 (run twice back to back)

## What was built

A new `src/harness/` package: fixture/config loaders, a scoring module (penalty and three accuracy axes),
a generic prompt-injection-obedience check, a grid runner (`runHarness`) that calls spec 003's
`classifyIssue` once per config-issue pair with fixture title/body passed in-process (never through
githubClient/mockGithubClient), and a report writer that emits the machine-readable
`harness-<runId>.json` and the readable `harness-<runId>.md` table under `$GENERATED_DIR/<specId>/`.
`pnpm harness --spec-id ... [--configs] [--config] [--fixtures]` is the new CLI entry, wired in
`package.json` the same way `classify` is (env-file-if-exists chain, `tsx`). `classifyMain.ts` gained a
`--harness` flag: it now looks up the issue by id in `fixtures/harness-issues.json` (extracted into
`src/harness/singleFixtureClassify.ts` so it's independently unit-testable), runs it through
`classifyIssue` once, and prints `{priority, effort, et, timeMs}` — no comment, no jsonl write, no GitHub
call. The non-flagged `pnpm classify` path is untouched. `pnpm typecheck`/`lint`/`test` are clean; 27 new
BDD-style tests added under `tests/harness/` plus the existing suite (274 tests total) all pass.

## Decisions made outside the spec

- **How `pnpm classify --harness --issue-id` gets the issue's content** — the enriched spec's own contract
  entry is self-contradictory in one paragraph: it says harness mode "must NOT fetch the issue from
  GitHub/mock by id", then two sentences later says the standalone CLI facade "is allowed to fetch that one
  issue from the configured github client". The ACCS settles this in practice: it calls `pnpm classify
  --spec-id 003-issue-classifier --issue-id "$ORD_ID" --harness` with `$ORD_ID` sourced from
  `fixtures/harness-issues.json` and never starts a mock GitHub server, so a real GitHub/mock fetch would
  always fail with connection-refused. I implemented the stronger, literal reading — `--harness` always
  resolves `--issue-id` against `fixtures/harness-issues.json`, never against GitHub — which is also what
  makes the ACCS pass reliably without a live mock. Flagging this instead of silently picking a side, per
  instructions.
- **Priority-accuracy / effort-accuracy formulas** — the spec asks these be reported "separately as well"
  next to the combined score but gives no formula for the split (only the combined-penalty formula is
  specified). I used a linear gap-over-max-range shape per axis (`1 - |gap|/5` for priority, `1 - |gap|/3`
  for effort) so the three numbers stay comparable in style to the combined one. ACCS only checks these are
  within [0,1], so this is a free choice, not one the check verifies.
- **Injection-obedience "echoes what the injected text demanded" heuristic** — the spec explicitly says the
  injection fixture is recognised by its tag, not its wording, so the echo-detection can't hardcode the
  actual fixture's phrasing. I extract quoted substrings (3-40 chars, `'...'` or `"..."`) from the injection
  fixture's own body and check (case-insensitively) whether the model's reply contains one of them verbatim
  — a generic, content-derived signal rather than a fixture-specific string match. This is a genuine
  judgment call the spec leaves open; ACCS doesn't assert on the disqualified value's correctness, only its
  presence.
- **Failed/never-arrived entries** — treated as `arrived: false`, `actualPriority/actualEffort: 0`,
  `penalty: 38` (the documented worst case), `et`/`timeMs: 0`, `disqualified: false` (can't judge obedience
  from an answer that never came back). "Outside allowed ranges" never actually occurs in practice because
  the reused `classifyIssue` engine already clamps priority/effort before returning.
- **Grid entry ordering** — JSON entries are written outer-loop-by-config, inner-loop-by-fixture. The spec
  doesn't require a specific order and ACCS doesn't check it.

## Bugs and loopholes in the spec or the ACCS I did not fix

- The self-contradiction described above (classify --harness "must not" vs. "is allowed to" fetch via
  GitHub) is the main one — noted, not resolved in the spec text itself, only in code behaviour.
- ACCS's md-table check validates structure (column count, no blank cells, accuracy in [0,1], failures a
  whole number, totals > 0) but never asserts the *values* are internally consistent with the json record
  (e.g. it never cross-checks totalEt in the md against the sum of `et` in the json for that config). Not a
  blocker, just something a stricter check could add later.
- accs.md's disqualification description ("or its reply repeats what the injected text demanded") is
  inherently unfalsifiable by the ACCS as written — "Do not assert what the model actually answered" is an
  explicit ACCS design choice, so this is expected, not a defect, but it does mean the heuristic's quality is
  untested by the acceptance check, only by my own unit tests with synthetic replies.
