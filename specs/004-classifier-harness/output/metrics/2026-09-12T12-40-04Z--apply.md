## Bugs and loopholes in the spec or the ACCS

- **Contract** "fixtures/harness-issues.json | Array of { id, title, body, expectedPriority (0-3), expectedEffort (0-3), tags[] }" — The real fixtures/harness-issues.json nests scoring data as `"expected": { "priority": N, "effortEst": N }`, not flat `expectedPriority`/`expectedEffort` fields. Any harness built to the contract's shape reads undefined for every fixture's expected values.
- **Method** "EXP_P=$(jq -r --arg id "$ID" '.[] | select(.id == $id) | .expectedPriority' "$FIXTURES_FILE")" — This jq query returns `null` for every fixture in the actual file since the field lives at `.expected.priority`. The check only guards against `null` for the injection/ordinary id lookup earlier, not here, so this silently compares null-to-null instead of catching the mismatch.
- **Scope** "**Is expectedPriority 0-3 or 1-3 like effort was before this spec?** 0-3, since the spec explicitly widens effort to 0-3 to pair with expectedPriority 0" — src/issue-tracker/llmClassifier.ts already clamps priority to 0-5 (`Math.min(5, Math.max(0, n))`), and the real fixtures use that same 0-5 scale (fixtures 1 and 2 have expected priority 5). The enricher's assumed 0-3 range was never checked against the existing classifier or fixture data and disagrees with both.

## Why it stopped

The enriched-spec's Contract section declares a fixture shape and priority range that conflict with the fixtures/harness-issues.json file already committed in the repo (nested expected.{priority,effortEst}, range 0-5) and with spec 003's classifier (clamps priority 0-5), so accs.bash's own fixture lookups return null regardless of harness code.
Re-run enrichment for 004-classifier-harness after deciding whether fixtures/harness-issues.json gets reshaped to flat expectedPriority/expectedEffort in 0-3, or the contract/accs.bash get rewritten to read expected.priority/expected.effortEst in the classifier's real 0-5 range.
